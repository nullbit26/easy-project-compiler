# Eval: контекст старого и нового отбора

`npm run eval` — шесть фикстурных проектов, две стратегии контекста, один отвечающий.

```
npm run eval                 # офлайн-заглушка, tsc для TS-кейсов
npm run eval -- --live       # тот же eval, но отвечает настроенный AI-провайдер
npm run eval -- --fast       # без tsc
npm run eval -- --json       # отчёт объектом, удобно диффать между прогонами
```

## Что он меряет

- **recall** — попал ли в промпт файл, без которого задачу нельзя решить (`needsContext`).
- **pass@1** — прошёл ли ответ одну попытку: сначала объявленные проверки кейса, затем `tsc --noEmit`
  для TypeScript-кейсов.
- **размер** — сколько файлов и символов реально ушло в промпт.

Стратегии: `legacy` — замороженная копия прежнего отбора (до 8 названных файлов, 60 000 символов,
400 путей по алфавиту); `graph` — `planTaskContext` из `server/services/`.

## Что он не меряет

Офлайн-заглушка (`answerFromVisibleFiles`) правит только те файлы, тело которых было в промпте.
Это детерминированная модель «вижу — правлю, не вижу — нет», а **не** оценка какой-либо реальной
модели: её pass@1 почти повторяет recall по построению. Кейсы подобраны под один класс ошибок —
«задача назвала один файл, а нужен второй», — поэтому 0/6 → 6/6 говорит о механике контекста, а не
о продуктивности агента. Реальную цифру даёт только `--live`, и её надо мерить на нескольких
моделях, а не на одной.

## Как добавить кейс

В `cases.ts`: `files` (проект целиком), `task.targetFiles` (что названо), `needsContext` (что обязано
попасть в контекст и почему), `solution` (полный эталонный патч), `checks` (строки, которые обязаны
быть в итоговых файлах). Кейс обязан стартовать компилирующимся и не проходить собственные проверки
до патча — это пиннят тесты `src/tests/evalHarness.test.ts`.
