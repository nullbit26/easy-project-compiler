# Lovable

**Поверхность:** конструктор · **Ссылка на файл:** обычный путь (плюс `@` внутри проекта) ·
**Файл правил:** `AGENTS.md` (читает и `CLAUDE.md`)
**В списке приложения:** «Lovable»

## Главное

Lovable собирает и правит проект сам, поэтому полные файлы в промпте не нужны — нужны намерение и
границы. Их собственный гайд формулирует это резче всех: **«make one meaningful change at a time»** и
явно «specify what to build, where, and what must stay untouched».

## Что говорит документация (октябрь 2026)

- **Одно изменение за раз.** Планируйте путь пользователя, промптьте **по компонентам**, а не целой
  страницей, добавляйте слой за слоем. Границы описывают так: «изменяем только эту страницу, её
  оформление оставляем, остальное приложение не трогаем»
  ([Prompting best practices](https://docs.lovable.dev/prompting/prompting-one)).
- **Режимы.** **Chat** — обсуждение без изменений кода; **Plan** — структурированный, редактируемый
  план, который утверждается до правок; **Build** — реализация с проверкой (раньше назывался Agent
  mode) ([Chat mode](https://docs.lovable.dev/features/chat-mode), [Plan mode](https://docs.lovable.dev/features/plan-mode),
  [Build mode](https://docs.lovable.dev/features/agent-mode)).
- **Контекст.** Внутри проекта код можно упоминать через `@`; можно приложить макет, скриншот или
  документ для сборки — бриф по продукту, PDF или Word. Для постоянного контекста есть knowledge
  проекта (краткий бриф: продукт, пользователи, сценарии, оформление)
  ([Project chat](https://docs.lovable.dev/features/projects/chat), [Knowledge](https://docs.lovable.dev/features/knowledge)).
- **Файлы правил.** Корневой `AGENTS.md` читается всегда; в списке возможных источников указан и
  `CLAUDE.md`. Приоритет между ними документация не описывает
  ([Define workspace and project knowledge](https://docs.lovable.dev/features/knowledge)).
- **Проверка.** Build mode описывается как «реализует и проверяет»; при этом тесты запускаются по
  запросу — браузерные для пользовательских сценариев, фронтенд-тесты для правил интерфейса,
  вызовы и краевые случаи для бэкенда. Подходящую проверку выбираете вы
  ([Test and verify](https://docs.lovable.dev/features/testing)).
- **Организация работы.** Несколько изменений — одним сообщением, а не потоком быстрых уточнений
  ([Project chat](https://docs.lovable.dev/features/projects/chat)).

## Промпт

````markdown
## Что изменить
На странице отчёта — кнопка «Экспорт» в шапке, скачивает CSV со всеми отфильтрованными строками.

## Где
Только страница отчёта: панель шапки и таблица. Новый компонент — отдельным файлом рядом с таблицей.

## Что не менять
Оформление страницы и таблицы, фильтры, навигацию, другие страницы. Логику загрузки данных не трогать.

## Как понять, что получилось
Нажатие скачивает report.csv с заголовком и текущими строками; при пустом результате — файл из одного
заголовка, без ошибки.

## Оформление
Использовать существующие кнопки и отступы приложения, не вводить новую библиотеку компонентов.
````

Если неясно, как встроить изменение в текущее устройство приложения — начните в **Plan** и утвердите
план, а не правильную догадку.

## Чего не делать

- не просить «сделать красиво» или «улучшить дашборд»: нужен наблюдаемый результат;
- не описывать сразу пять изменений в одном сообщении: гайд просит одно осмысленное изменение за раз;
- не требовать «полный код файла» — Lovable пишет код в проект сам;
- не рассчитывать, что он угадает, что нельзя ломать: перечисляйте защищаемые места (навигация, вход,
  оформление);
- не начинать с Build там, где ещё не решено, что строить: Chat дешевле плана, план дешевле отката.
